# Playbook: LLM infra 上游 PR

适用于给 verl、Megatron-LM 这类上游项目提交 PR。通用规则见 [KERNEL](../KERNEL.md)；这里只写上游 PR 特有的部分。

## 1. 认领

- 先确认 issue 或 roadmap 子项仍然开放，没有其他人的 PR 在做同一件事（搜 open PR 和关联的 issue）。
- 范围不清楚时，先在 issue 下留言，写清打算做什么、不做什么，等 maintainer 回应后再写代码。对外发言属于人工关卡，由人发出。
- 一个 PR 只解决一件事。大功能拆成可以独立合并的几步。

## 2. 读上游约定

动手前读 CONTRIBUTING、PR 模板、pre-commit 或 lint 配置、CI workflow，以及是否要求 DCO 签名或 CLA，并记下：

- 本地需要跑哪些检查；
- 哪些测试需要 GPU，CI 里谁能触发它们。

代码风格跟随邻近代码，不顺手重构无关部分。

## 3. 复现基线

- 在上游最新 HEAD 上复现问题，或测出基线数字。记录 commit、硬件（GPU 型号和数量）、CUDA、PyTorch 和关键依赖版本，以及并行配置（TP/PP/DP/EP 等）。
- 本地没有所需硬件时，写清实际跑了什么、没跑什么，对应 claim 标 `ENV-BLOCKED`，不要拿小配置的结果冒充。

## 4. 分工

- 人：确定根因假设、接口和设计取舍，写关键代码或审定 agent 写的关键路径。
- agent：读代码、给出最小复现、扩大测试覆盖、跑矩阵、整理证据，并对人的假设提出反例。

## 5. 证据分层

按 PR 的 claim 选择需要的层，每层都要有实际输出：

| claim | 证据 |
|---|---|
| 行为正确 | 新增或修改的单测在修复前失败、修复后通过；上游相关测试全部通过 |
| 数值不变或对齐 | 同 seed、同配置下与基线比较 loss 或 logits，写明 dtype 和容差；训练类改动给出若干 step 的 loss 曲线对比 |
| 性能提升 | 同硬件、同配置、预热后多次测量；报告吞吐（tokens/s 或 samples/s）、显存和波动，不只挑最好的一次 |
| 分布式或兼容 | 覆盖 PR 声称支持的并行配置和后端，没覆盖到的写进限制 |

## 6. 写 PR

PR 描述包含：

- 动机，并链接 issue；
- 改了什么；
- 证据：命令、硬件和数字；
- 限制和未验证项；
- 是否破坏兼容。

描述的写法遵循写作体系（见 README）。草稿交给人审定后再开 PR。

## 7. Review 与收尾

- 逐条回应 review：改了的说明改在哪里，不同意的给出理由和证据。推送新提交，不 force-push 掉 reviewer 已经看过的历史，除非上游要求 squash 或 rebase。
- 上游 CI 失败时，先区分是自己的问题、flaky 还是基础设施问题，再处理；不把未运行的检查写成通过。
- PR 合并或关闭后，在看板更新状态，并按 [retro 模板](../retro/TEMPLATE.md) 写复盘。
