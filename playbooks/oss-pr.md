# Playbook: LLM infra 上游 PR

适用于给 verl、Megatron-LM 这类上游项目提 PR。这里列的是上游 PR 特有的检查点，不是固定流程：顺序和做法自己决定，有更好的办法就用更好的办法。通用规则见 [KERNEL](../KERNEL.md)。

## 认领前

- 确认 issue 或 roadmap 子项仍然开放，也没有别人的 PR 在做同一件事。
- 范围不清楚时，先在 issue 下和 maintainer 对齐，再写代码。一个 PR 只解决一件事。

## 上游约定

读 CONTRIBUTING、PR 模板、lint 和 pre-commit 配置、CI，以及 DCO 或 CLA 要求，弄清两件事：

- 本地要跑哪些检查；
- 哪些测试需要 GPU，由谁触发。

代码风格跟随邻近代码。

## 基线

先在上游最新 HEAD 上复现问题，或测出基线数字，并记录：

- commit；
- 硬件；
- CUDA、PyTorch 等关键依赖的版本；
- 并行配置。

缺少所需硬件时，写清实际跑了什么，对应的 claim 标 `ENV-BLOCKED`，不要拿小配置的结果冒充。

## 证据

按 PR 的 claim 选用下表中的证据，每一项都要有实际输出：

| claim | 证据 |
|---|---|
| 行为正确 | 新测试在修复前失败、修复后通过；上游相关测试全部通过 |
| 数值对齐 | 同 seed、同配置下与基线比较 loss 或 logits，写明 dtype 和容差 |
| 性能提升 | 同硬件、同配置，预热后多次测量；报告吞吐、显存和波动 |
| 分布式或兼容 | 覆盖 PR 声称支持的配置，没覆盖的写进限制 |

## PR 与 review

- PR 描述写清动机、改动、证据（命令、硬件、数字）、限制，以及是否破坏兼容。写法遵循 writing-system。
- 逐条回应 review，不同意时给出证据。CI 失败先分清是自己的问题、flaky 还是基础设施问题。
- PR 合并或关闭后更新看板，并写复盘。
