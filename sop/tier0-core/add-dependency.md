# SOP-add-dependency: 引入一个依赖

- **层级**: tier0-core
- **落实纪律**: P1(契约先行:先声明为什么要)+ P4(可追溯:锁定并记录)
- **绑定骨架**: 无(被 release-version 依赖)
- **通用性档位**: U1(假设有依赖管理,不绑具体生态)
- **版本**: v1

## 触发条件

需要新增一个第三方依赖(库/框架/工具/服务)时。

## 前置条件

- 当前依赖清单与锁文件状态已知(见 `→ tier0-core/lock-env.md`);
- 有一个明确的功能需求驱动本次引入。

## 依赖 SOP

→ tier0-core/lock-env.md(引入后必须重新锁定)。

## 步骤

1. 写引入理由(P1 的最小契约):**为什么需要它、解决哪条需求、有无更轻的替代(标准库/已有依赖)、不引入的代价**。理由记入 `{DECISIONS}`(ADR)或 PR 描述。
2. 评估准入:许可证是否兼容 `{LICENSE_POLICY}`、维护活跃度、传递依赖规模、供应链风险(来源可信、版本可锁哈希)。任一硬性项不过 → 不引入。
3. 固定版本区间:给出精确版本或带上界的兼容区间,禁止无上界/`latest`。
4. 声明式加入依赖清单,执行 `→ tier0-core/lock-env.md` 刷新 `{LOCK_FILE}`。
5. 加一条最小 smoke:真实调用该依赖一次,证明"这个 API/签名真的存在且行为如此"(防似是而非的幻觉 API)。
6. 记录到可追溯位置:依赖名 + 版本 + 引入理由 + 对应需求(P4)。

## 门禁

[REVIEW] 必问:"这个依赖对应哪条需求?有没有更轻的替代?许可证/供应链过关吗?"
[AUTO] 引入后 `{LOCK_FILE}` 已更新;无未锁定/浮动版本;smoke 通过。

## 完成判定

- 依赖已锁定精确版本并入 `{LOCK_FILE}`;
- 引入理由 + 需求映射有据可查;
- smoke 通过(二值)。

## 失败处理

遵守 P3:若许可证/供应链/维护性硬性项不过 → 明确拒绝引入并报告原因,不得"先加上跑通再说";若 smoke 证明该 API 不存在或行为不符 → 中止,不得基于文档/类型假设"应该能用"就写下去;若无法锁定精确版本 → 按 lock-env 的失败处理报告风险,不静默用浮动版本。

## 产物

更新后的依赖清单 + `{LOCK_FILE}` + 引入理由记录(ADR/PR)+ 一条 smoke 用例。
