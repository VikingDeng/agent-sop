# SOP 质量方法论(写 SOP 的元规范)

> 来源:《agent-sop_tier0细化与质量方法论_v1》(桌面施工单)。本文件回答三件事:一条 SOP 写到什么程度算合格、如何保证它合格、通用性与质量如何兼得。
> 原则:**先定"合格的定义"和"通用性刻度",再动手写**。本文件自身就是方法的自证——可用 §1 验收清单逐条卡任何一条 SOP 成品。
> **版本**: v6。相对 v5 删除与运行时 Kernel 重复的 checkpoint 状态表；SOP 只保留结果语义、触发条件和失败路径，长程恢复由平台 Adapter 在确有生命周期需要时提供。
> **运行时边界**:本方法论的 8 字段用于让 SOP 本身可导航，不要求执行任务时制造八份 artifact、逐步台账或独立 checkpoint 文件。用户/项目契约之下，运行时适用性统一由 `tier0-core/autonomous-supervisor.md` 判断。

## §1 一条 SOP 的验收标准(A1-A7)

一条 SOP 合格,当且仅当同时满足下列 7 条。**这是全仓 SOP 的通用验收清单**。

| # | 验收项 | 判据(客观) | 反例(不合格) |
|---|---|---|---|
| A1 | **8 字段齐全** | 触发/前置/依赖/步骤/门禁/完成判定/失败处理/产物,一个不缺 | 缺"失败处理"或写"TODO"充数 |
| A2 | **纪律映射准确且非虚标** | 头部声明的 P1-P4,在步骤或门禁里能找到对应动作 | 声明 P3 但步骤里没有任何"失败即报"的机制 |
| A3 | **自由度与脆弱性匹配** | 多路径、探索型任务用原则与启发式；脆弱、不可逆操作才规定精确步骤 | 给探索任务写死唯一 action order |
| A4 | **完成判定有匹配 claim 的证据** | Agent 能通过命令、状态、复现、统计或明确 review 判据判断质量 | 只检查 artifact 存在，不检查用户要的结果 |
| A5 | **失败处理体现 P3** | 禁止隐藏失败和静默降低标准；允许显式、等价、可重新验收的 retry/fallback | 模型不可用就把整个项目判失败，或用旧结果冒充新结果 |
| A6 | **依赖用引用不复制** | 依赖的其它 SOP 用 `→ tierX/name.md` 指向,不把对方内容抄进来 | 把 commit-and-pr 的步骤复制到 package-submission |
| A7 | **通用性档位明确** | 头部标注适用档位(见 §3),步骤里把"可变的具体值"抽象成参数/占位 | 步骤写死 `pytest tests/`(不是所有项目用 pytest) |

> **A2 是重点**:它把 PRINCIPLES 的"收纳判据"从入库时的一次性检查,变成了每条 SOP 内部的强约束。声明纪律 ≠ 落实纪律,必须在正文里能指认落点。

## §2 质量保证机制(L1-L4)

质量不能靠"认真写了",要靠**机制 + 可复核痕迹**。四层机制正好是 P1-P4 各自的自我应用——如果一套纪律连"写自己的 SOP"都约束不住,它就不配当全仓地基。

### L1 — 模板即契约(P1 的自我应用)

每条 SOP 使用 `_TEMPLATE.md` 的 8 字段作为导航结构，让触发、证据、边界和产物容易查找。字段不是要求 Agent 制造八份 artifact，也不意味着每个字段都必须成为 gate。

### L2 — 纪律回指检查(P2 的自我应用)

对每条 SOP 做一次"独立 oracle"式反向核对:**不看头部声明,只读步骤和门禁,反推它实际落实了哪几条纪律,再和头部声明比对**。不一致 → 要么头部虚标(改声明),要么正文没落实(补步骤)。把 P2"禁止被测对象自证"用在文档自己身上——看它"做"了什么,不看它"说"了什么。

### L3 — 失败路径审查(P3 的自我应用)

逐条检查“失败处理”字段，确认没有伪造、吞掉失败或静默降低成功标准；同时避免把显式、质量等价的 retry/fallback 误判为违规。使用 `no-fallback-review` 审查语义，而不是按关键词零容忍。

### L4 — 可追溯留痕(P4 的自我应用)

每条 SOP 头部有版本号;每次改动进 commit;方法论文档本身就是"为什么这么写"的 ADR。下一个 agent/session 读它就知道细化的判据,不会跑偏。

### 诚实边界(遵守 P3)

- **不能**保证步骤里引用的具体工具命令在真实环境一定能跑通(如 ruff/nsys 版本差异)——要 agent 在真实项目跑一次 smoke 才算验收。文档把这类"环境相关"点显式标出,不假装成立。
- **不能**替代对"纪律映射对不对"的最终判断——做到 L2 的机器可查 + 反向核对,终审权在人。
- **SOP 自身的验证是单样本的(复诊局限)**:一条 SOP 的质量目前靠一次 CDR(codex deep review)+ 一次真实项目 smoke 检验,样本量 = 1,其结论方差未知。真正的复诊应是"同一 SOP 让 N 个不同 agent 各跑一遍施工,看产出方差"(即 B 轨"跑 5 遍测方差"用在 SOP 上),但这在当前 agent 施工成本下跑不起。因此:采信任何单次 CDR 结论时按"单样本、方差未知"打折,CDR 揪出的洞视为"这次 agent 的表现",需真实项目复现后才升级为"SOP 的系统缺陷"。**这是显式声明的已知局限,不是一个已建成的复诊机制**——不假装 §2 里有一层它其实没有的保证。等 agent 批量重跑便宜到可承受时,再把复诊从 note 升级为机制。

## §3 通用性 × 质量的张力

### 3.1 张力

- **通用性拉高** → 适用面广,但滑向"正确的废话"("确保代码质量"适用于一切,等于没说),**质量塌了**。
- **质量拉高** → 具体可执行,但绑死场景("跑 pytest -x tests/unit"只对 pytest 项目成立),**通用性塌了**。

天真的做法是二选一或"取中间",都错。正确解:**把通用性做成分层结构,"通用的原则"和"具体的实现"物理分离,各自都做到高质量。**

### 3.2 通用性分层(不是滑块)

| 层 | 内容 | 通用性 | 质量表现 | 谁负责 |
|---|---|---|---|---|
| **纪律层(P1-P4)** | 为什么这么做 | 最高(跨所有项目/活动) | 质量="是否揭示了本质约束" | PRINCIPLES.md |
| **SOP 不变式层** | 结果标准、证据要求、风险边界与策略选择启发式 | 高(跨同类任务) | 质量="是否稳定结果又保留合理探索空间" | 每条 SOP |
| **参数/recipe 层** | 具体命令、具体工具、具体阈值 | 低(绑定技术栈/项目) | 质量="是否真能跑通" | 项目级 Agent 指令文件 / recipe/ 填 |

**关键手法:一条 SOP 只写"不变式层",把"参数层"抽象成占位符,由项目在引用时注入。**

例——`lock-env` 的步骤不该写死:
- ❌(正确的废话):“环境要可复现”。
- ❌(质量塌/绑死):“所有任务运行 `uv lock`，生成 uv.lock 并在干净 CI 从零重建”。
- ✅(分层):“从当前 claim 反推 outcome-relevant 环境表面，保存本次 resolved identity；当 claim 要求未来/跨环境可重建，或有具体环境漂移 failure path 时，使用项目原生 `{LOCK_CMD}` / `{LOCK_FILE}` 并运行匹配的 rebuild Oracle。具体工具由项目级 `AGENTS.md` 注入（如 Python+uv → `uv lock` / `uv.lock`）。”

第三种写法同时保留共同下界与比例化强度：每个 evidence-bearing run 都有可复核的实际 identity；lockfile、CI rebuild 或独立环境只在对应 claim/risk 下成为不变式。参数由项目注入，避免把一种生态配方升级成全仓门禁。

### 3.3 通用性档位

每条 SOP 头部标注档位,避免"写多通用"靠感觉:

- **U0 普适**:不含任何技术栈假设,纯不变式(如 `no-fallback-review` 的"任何出错路径都不得静默产出结果")。
- **U1 语言/生态相关**:假设大类生态但不绑具体工具(如"用项目的包管理器锁依赖")。
- **U2 项目相关**:必须由项目注入具体参数才能执行(如"跑项目的验收测试集")。

档位越低越通用。**规则:能写成 U0 的不写成 U1;必须落到 U2 的,把 U2 部分显式标成 `{参数}` 交给项目,SOP 主体保持在 U0/U1。** 这样一条 SOP 的"骨"是高通用高质量的,"肉"由项目补,张力被结构性化解。

### 3.4 反面红线(通用性不能牺牲的东西)

无论多通用,下面三样**永不能被抽象掉**:

1. **失败诚实**(P3):任何档位都不得伪造、隐藏失败或静默降低成功标准；显式等价替代可以继续。
2. **完成判定的可自查性**(A4):可以不写死命令，但证据必须足以支持实际 claim；探索性结论允许带不确定性而非伪装二值。
3. **纪律映射**(A2):再通用也要能指认落实了哪条纪律,否则就是孤儿 SOP。

## 执行粒度：结果契约，不是 checkpoint 状态机

运行时统一服从 `tier0-core/autonomous-supervisor.md`。明确请求、issue、proposal、spec 或现有测试可以直接承载 compact contract；方向已冻结且工作可逆时立即执行，不为展示流程而命名 checkpoint、重复确认或生成状态文件。只有命中 Kernel 的真实未授权分叉才等待人。

长任务也不预写固定阶段链。只有真实跨 session、外部 scheduler、不可廉价重做的工作或交接需要时，才在项目原生载体中保存足以恢复的契约、工作区/工件身份、已完成与未完成证据、下一判别动作和授权 blocker。具体 lifecycle 与 retry 语义属于平台 Adapter；SOP 作者不得把 package、phase、role、hash 或 handoff 文件升级成通用质量门禁。

## 重内容下沉:references 边车

当一条 SOP 需要附带穷举型长内容(样板模板、维度清单、配方表)时,不把长内容写进 SOP 正文,而是下沉到同级 `references/` 子目录,SOP 正文只留 8 字段骨架 + 一行指引(如"详见 references/xxx.md")。

理由:SOP 正文承载"流程与判据",应保持可快速通读;穷举细节撑大正文会淹没判据。这与"PROSE_STANDARD 被引用而非复制"是同一架构,只是下沉到文件级。

适用信号:某字段(通常是"步骤"或"门禁")的附属清单超过正文主体篇幅时,即应下沉。

## §4 使用方式

1. 细化任何一条 SOP 前:定档位(U0/U1/U2)→ 用 §3.2 的分层手法写不变式层 → 参数 `{化}` → 写完对照 §1 的 A1-A7 逐条自检(自检结论附在文件末尾或 commit message)。
2. 质量自查走 §2 的 L1-L4。
3. 后续按同法分批细化剩余 SOP。
