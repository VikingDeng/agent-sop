# SOP-ops-incident: 故障处置与复盘

- **层级**: tier2-activity
- **落实纪律**: P3(故障不带病降级运行、如实上报)+ P4(处置与根因可追溯)
- **绑定骨架**: 无
- **通用性档位**: U0(故障处置流程普适)
- **版本**: v1

## 触发条件

既有系统发生故障/事故(监控告警升级、用户影响、数据异常)时。

## 前置条件

- 有故障现象与影响范围的初始信息;
- 有升级路径 `{ESCALATION}` 与止血手段清单。

## 依赖 SOP

无(是运维链路的兜底;可由 ops-monitor-rollback 升级进入)。

## 步骤

1. 定级与止血优先:先按影响面定级,**优先止血(回滚/隔离/限流)恢复服务**,再查根因——顺序不能反。
2. 如实上报:按 `{ESCALATION}` 通报,信息包含真实影响面,不得缩小或隐瞒(P3)。
3. 保留现场证据(日志/指标快照/时间线),供根因分析,不清场。
4. 根因分析:用证据定位,区分直接原因与根本原因;禁止"重启好了就结案"而不查根因。
5. 复盘产出:时间线 + 根因 + 止血措施 + 长期改进项(可追踪),入 `{POSTMORTEM}`(P4)。

## 门禁

[REVIEW] 必问:"是真定位了根因,还是重启/自愈掩盖了问题?影响面上报是否如实?"
[HUMAN] 定级与对外通报口径人工把关。
[REVIEW] 产出符合 → PROSE_STANDARD.md(复盘 postmortem 正文)。

## 完成判定

- 服务已恢复(止血确认);
- 复盘含根因 + 改进项且可追踪(二值:postmortem 文件 + 改进项台账)。

## 失败处理

遵守 P3:故障期禁止"带病降级继续跑"冒充可用——要么止血恢复,要么如实标注降级范围并上报,不得对外假装正常;根因未定位就结案 → 不允许,标记为"根因待查"继续跟进;上报缩小影响面 → 违规。

## 产物

故障记录 + `{POSTMORTEM}`:时间线 + 影响面 + 根因 + 止血 + 可追踪改进项。
