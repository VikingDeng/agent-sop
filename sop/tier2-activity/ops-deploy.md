# SOP-ops-deploy: 部署变更到既有系统

- **层级**: tier2-activity
- **落实纪律**: P1(变更先有 runbook + 回滚预案)+ P4(部署可追溯)
- **绑定骨架**: 无
- **通用性档位**: U1(部署动作通用,目标系统/工具参数化)
- **版本**: v1

## 触发条件

需要把一个变更(配置/版本/开关)应用到既有的、已在运行的系统时。

## 前置条件

- 变更内容已确定且版本可追溯(`{CHANGE_REF}`:commit/工单/版本号);
- 变更已在非生产环境按 `→ tier0-core/reproduce-result.md` 验证过行为;
- 存在 `{RUNBOOK}`(部署步骤)+ 回滚预案。

## 依赖 SOP

→ tier0-core/reproduce-result.md(部署前变更行为已复现验证)。

## 步骤

1. 前置校验:确认回滚预案存在且可执行、变更窗口/审批就绪、当前系统健康基线 `{HEALTH_BASELINE}` 已记录。
2. 按 `{RUNBOOK}` 执行部署(灰度/分批优先:先小流量/单实例,再全量)。
3. 每一步后核对健康信号 `{HEALTH_CHECK}`(既有系统的监控/探针,不在沙箱新起服务):关键指标未劣化才继续下一批。
4. 全量后观察 `{SOAK_WINDOW}`,与 `{HEALTH_BASELINE}` 比对确认无回归。
5. 记录部署台账:`{CHANGE_REF}` + 时间 + 批次 + 健康对比 + 结果(P4)。

## 门禁

[RUNTIME] 每批部署后 `{HEALTH_CHECK}` 通过才继续;失败即触发回滚。
[REVIEW] 必问:"回滚预案验证过吗?健康判据是既有监控给的客观信号还是'看着没事'?"

## 完成判定

- 变更全量部署且 `{SOAK_WINDOW}` 内健康指标不劣于基线;
- 部署台账记录完整(二值)。

## 失败处理

遵守 P3:任一批次健康检查劣化 → **立即按预案回滚**,不得"再等等看说不定自己好"(带病降级运行=P3 违规);无回滚预案 → 不许开始部署,停在前置校验报告阻塞;部署工具报错 → 中止并回滚,不静默重试掩盖。**边界:本 SOP 不在沙箱内起任何监听服务,健康信号一律取自既有系统的监控。**

## 产物

部署台账:`{CHANGE_REF}` + 批次记录 + 健康对比 + 回滚(如触发)记录。
