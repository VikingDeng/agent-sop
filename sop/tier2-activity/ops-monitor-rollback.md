# SOP-ops-monitor-rollback: 监控与回滚判定

- **层级**: tier2-activity
- **落实纪律**: P2(用客观监控信号判健康,不靠主观)+ P3(异常不静默吞、该回滚就回滚)
- **绑定骨架**: 无
- **通用性档位**: U1(监控指标/阈值参数化)
- **版本**: v1

## 触发条件

既有系统运行期需要判断"是否健康、是否该回滚/告警"时;或部署后的观察期。

## 前置条件

- 已定义关键指标 `{SLI}` 与告警阈值 `{SLO_THRESHOLD}`(延迟/错误率/饱和度/流量);
- 已有可回滚的上一稳定版本 `{LAST_GOOD}`。

## 依赖 SOP

无(与 ops-deploy 配合:部署观察期调用本 SOP 判定)。

## 步骤

1. 采集 `{SLI}` 客观信号(取自既有监控系统,不在沙箱新起采集服务)。
2. 对每个指标与 `{SLO_THRESHOLD}` 比对,判健康/劣化/告警三态。
3. 劣化达回滚条件 → 执行回滚到 `{LAST_GOOD}`,回滚本身也验健康。
4. 告警必须**送达且被确认**,不得静默吞掉(P3):无人确认的告警视为未处理。
5. 记录:触发的指标 + 判定 + 处理(回滚/告警/无操作)+ 时间。

## 门禁

[RUNTIME] 指标越阈即触发对应动作(告警/回滚),不得压制。
[REVIEW] 必问:"健康判定基于客观 SLI 还是主观感觉?告警有没有被静默过滤?"

## 完成判定

- `{SLI}` 已对阈值判定;
- 达标动作(回滚/告警)已执行且记录(二值)。

## 失败处理

遵守 P3:指标越阈却"觉得问题不大"不处理 → 违规,必须按阈值动作;告警被静默吞/降噪过度导致漏报 → 违规,告警不得无声消失;回滚后仍不健康 → 升级为故障,进 `→ ops-incident`,不得"回滚了就当没事"。**边界:监控信号取自既有系统,不在沙箱起监听/采集服务。**

## 产物

监控-判定记录:`{SLI}` 值 + 阈值判定 + 动作(回滚/告警)+ 确认状态。
