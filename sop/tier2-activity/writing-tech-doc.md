# SOP-writing-tech-doc: 技术文档写作

- **层级**: tier2-activity
- **落实纪律**: P1(先定读者/目的/非目标/大纲)+ P4(每个技术论断可追溯到来源/代码)
- **绑定骨架**: 无
- **通用性档位**: U0(文档写作流程普适)
- **版本**: v1

## 触发条件

需要写技术文档(设计文档/API 文档/使用说明/规范)时。

## 前置条件

明确的写作对象(要文档化的系统/接口/流程)与可访问的事实来源(代码/spec/实测)。

## 依赖 SOP

无。

## 步骤

1. 契约先行(P1):先定**读者是谁、文档目的、非目标(不覆盖什么)、大纲**,四者定稿再写正文。
2. 正文对着事实来源写:每个技术论断(接口签名/行为/限制)可追溯到代码/spec/实测,不凭记忆或想象。
3. 示例可运行/可验证:代码示例应真实跑通过(防幻觉 API),不贴"看起来对"的伪代码冒充。
4. 与实现一致性核对:文档描述与当前代码行为一致(防文档漂移);不一致时以核实后的事实为准并更新。
5. 标注版本/适用范围,留可追溯痕迹(对应哪个版本/commit)。

## 门禁

[REVIEW] 必问:"每个技术断言有来源吗?示例真跑过吗?和当前代码一致吗?"

## 完成判定

- 读者/目的/非目标/大纲已定;
- 关键技术论断均可追溯来源;
- 示例可运行、与实现一致(二值核对)。

## 失败处理

遵守 P3:某技术论断查不到来源/无法验证 → 标注"待核实"或删除,不得凭印象写下当作事实;示例跑不通 → 修正或删除,不得贴伪代码冒充可用;发现文档与实现不符又无法立即核实 → 明确标注不一致风险,不静默按旧描述发布。

## 产物

一份技术文档:含读者/目的/非目标/大纲 + 有据的正文 + 可运行示例 + 版本适用范围。
