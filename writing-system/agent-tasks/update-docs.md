# 任务：检查并修复 docs 下的文档项目

用户用一句自然语言就能调用本文件，例如：

```text
按 docs 规范把 radar-data-gen 和 ai4ai 全面检查并修复，引用统一上标，完成后给 PDF 和未决清单。
```

本文件说明**一次任务做到什么程度、能改什么、怎么报告**；
详细判断标准在 [`document-quality.md`](../document-quality.md)，这里不重抄。

## 一、目标怎么定

- 项目以用户点名或当前上下文为准。用户说「这两篇」时只指当前这两个，不要把它固化成默认目标。
- 先从当前目录与上下文定位；仍无法确定目标时只问必要信息，同时继续做能独立完成的检查，
  不必等回答才开始。
- 常用参数都有缺省值（第七节），给了就覆盖缺省，没给就按缺省执行。

## 二、一次任务做到什么程度

「一轮」= 一次用户任务之内，允许多次局部修复与复查；不要求只改一次，
也不保证把所有无依据的缺口都修完。在同一请求里完成所有有依据的必要修复与复核；
缺证据的项标「待证」，不伪造依据，也不因此阻塞其余可做的工作。

循环执行，直到本次范围内没有可修的剩余问题。某一项阻塞时记录原因，继续其余独立工作：

1. 读规则与项目 README，确认本次范围；
2. 记录问题与证据：位置、现象、判定依据；
3. 直接实施有依据的修复；
4. 按项目 README 构建，并检查最终 PDF；
5. 对修复做回归：旧问题是否真的消失、有没有引入新问题。语言类修改还要检查**诊断与改稿是否对应**：
   指出了推理或信息问题，就确认最终段落真的解决，不能只调整密度或改换说法；
6. 剩余问题按状态表交付。

- **用户要求「检查并修复」就是已经授权写入**，审阅结果不再问一次确认；
  只有用户明确说只审阅、不要改文件时才不写。
- 问题计划写在报告里，不作为用户必须审批的阶段。
- 读规则时，用户当前指令优先于本文的缺省。
- 用户只提语言、某一章或某一类问题时，只做相关面与回归，不升级为全面论文审计。
- 能自己判断的按规范判断并直接改；只有取决于作者真实意图或缺失证据的才列入「待证」。

## 三、先读什么

| 文件 | 读它来定什么 |
|---|---|
| [`AGENTS.md`](../../AGENTS.md) | 目录骨架、模板选择、基线只读等硬规则 |
| [`document-quality.md`](../document-quality.md) | 引用、图、表、公式、证据、页面与交付残留的完整检查口径 |
| [`SKILL.md`](../skills/research-writing-pipeline/SKILL.md) | 读者中心的改写主线（判断 → 信息 → 措辞）、检查点与真实性边界 |
| [`document-genres.md`](../skills/research-writing-pipeline/references/document-genres.md) | 按读者任务定主文种：调研综述、工程技术文档、研究论文三类写法，混合内容按当前段落职责处理 |
| `<项目>/README.md` | 该项目的命令、结构、验收状态、已知问题 |

全面任务先定主文种，按所选文种审查全篇结构与提纲；各项先按读者任务、文种与交付要求判断是否
必需——不必需的记「不适用」，必需而缺失的按待修/待证报出，不得记「不适用」。摘要—正文—结论的
对应只在文稿实际有这两部分、或文种与投稿要求规定要有时才检查，要求有而缺失的要指出；手册、
任务指南、短 ADR 等确实无需摘要/结论时不补。再读目标章节及其上下文：前一节的内容、
本节的图表公式、下一节的开头；局部任务按相关范围阅读。
先弄清读者此刻的疑问是什么、已有信息够不够，再决定改哪里。

## 四、默认覆盖的检查面

「全面检查并修复」默认覆盖下表全部。这只是防漏清单，判断标准在 `document-quality.md`。
表内各项先按读者任务、主文种与交付要求判断是否必需：文种不需要的项记「不适用」，
必需而缺失的按待修或待证报出，不得标「不适用」。

| 面 | 检查什么 |
|---|---|
| 引用与参考文献 | 正文默认上标方括号、官方要求优先；编号映射、文献数据、证据支持关系、PDF 抽查（规范第一节） |
| 图 | 交付物与图源、导出与缺图门禁；各图种看什么（第二、三节） |
| 编号与引用 | 稳定 label、各类计数器与章节/附录内编号正确、有目的的引用（第四节） |
| 表 | 列口径、有效位数、缺测与 0 的区别、跨页与过宽（第五节） |
| 公式与符号 | 就地定义、量纲与索引、编号与引用（第六节） |
| 证据 | 主张 / 证据 / 限制可辨，论断强度不漂移（第七节） |
| 读者与语言 | 主文种对应的全篇结构与章节关系（因果递进、并列比较、操作先后、检索并列都合法）；摘要/结论按文种与交付要求判断是否必需，必需而缺失要报出；术语一致；判断 → 信息 → 措辞的语义验收（第八节，细则在写作技能） |
| 代码与算法 | 输入输出与正文一致，没运行的示例不算验证（第九节） |
| 最终 PDF | 封面目录、页码、缺字、上下标、孤立标题、表跨页、裁切、链接、参考文献（第十节） |
| 交付残留 | TODO、占位、缺图、生成器旁白、绝对路径（第十一节） |

## 五、能改什么，不能改什么

**文件范围按任务定**：正文与元信息、图片源与导出物、文献数据、项目专用样式与过滤器，
以及必要的 Makefile、tools、README 改动都在默认范围内。不要自行把完整修复收窄为 content-only。
**用户明确给了 content-only、只审阅等限制时，限制优先**；若完成某项修复需要越过限制，
先完成允许范围内的独立工作，说明具体还需改哪个文件及原因，不静默扩大权限。

**只改用户点名的项目**；其他项目有同类问题也不动，写进报告。

**默认保留现有引擎与模板。** 引用上标优先用项目已有配置或扩展接口实现；
改完检查全局 show rule 有没有误伤图表编号、脚注与区间。

**必须改锁定模板或过滤器时**（用户已请求修复，且不改就做不到）：

- 修改前保存相关文件与已有 PDF，先核对现有 lock；不匹配时查已有变更，来源不明的内容不自动信任；
- 有共享维护源的模板或工具，在真实源按来源规则修改、记录版本，只让目标项目显式升级；
- 项目自有过滤器或样式直接在项目内修，不要求迁到 `_shared/`；
- 确认源码变更及来源后再显式更新 `template.lock`，构建并验证修复与相关回归，保护基线、保留 diff。
  **不以消除报错为由重写 lock**；
- 不受影响的项目不跟随升级；
- 这类受控升级不再向用户要一次许可；超出授权的结构性大改才隔离出来单独报告。

**图**：可以按正文里已经写清的流程重绘示意图，标注自绘或改绘及依据；
不能伪称恢复了失踪的原图，也不制造研究数据。「不能编造图片」不构成阻止合法画图的理由。

**正文被有意修改后**，旧 PDF 的严格一致对比可能失败；逐项核对差异与本次改动及其分页影响，
检查无关内容是否丢失、数值与引用是否漂移，不能只把所有差异声明为「预期」。
`make verify` 可能把严格 compare 打包在内，要区分真缺图、真引用错误、真构建错误与预期变化。
不能删校验，也不能改基线让它变绿，更不能因此宣称正文不可交付。

## 六、报告与证据

- 保存修改前的文件与已有 PDF，证据落 `/tmp/<task>-<date>/`。
- 报告给：最终源版本、跑过的命令、结果、问题状态表。实际执行的和没有执行的分开写，
  不写没有证据的「全部通过」。
- 状态表分为：已检查无问题 / 已修复 / 待证 / 未检查 / 不适用，每条给位置与依据。
  全面检查仍按全项走；每项先按读者任务、文种与交付要求判断是否必需——不必需的记「不适用」，
  必需而缺失的按待修/待证报出，不得记「不适用」，也不为打勾制造内容。
- 语言类修正只列代表性例子：位置、原文问题、改动、依据；不为每句生成证明，
  也不用句式计数或「更自然」充当验收证据。删除了无依据的评价性内容、或把主张收窄为材料支持的范围时，
  说明这一实质变化；不静默改作者主张。
- 能自行查明的问题不要求用户逐项判断；待证项只提出无法自行补齐的证据或意图问题。
- 长任务把问题、状态与证据持续写入同一份记录，便于中断后续做，不只留在会话上下文里。
- 缺少影响结论的证据或尚未完成关键检查时，注明草稿或有限交付及具体影响，不宣称正式验收通过。
- 不额外生成大量报告文件，也不用固定输出模板。

## 七、常用参数

自然语言里说清即可，缺省如下：

| 参数 | 取值 | 缺省 |
|---|---|---|
| 项目 | 项目名，一个或多个 | 用户点名或当前上下文确定的项目 |
| 读者 | 目标读者及他们要完成的任务（调研选型/理解机制/评审实施/论证新贡献等） | 用户已说明，或据项目 README、源稿与上下文判断 |
| 文种 | 三类写法之一：调研综述 / 工程技术文档 / 研究论文 | 据读者任务与上下文判断，在报告里记录 |
| 交付目标 | 目标会议/期刊/学校/内部规范，含年份与 track | 沿用用户已指定或项目明确记录的目标；没有就沿用内部规范，不猜具体会议 |
| 任务 | 检查并修复 / 只审阅 / 润色 / 排版 / 修图 | 检查并修复 |
| 范围 | 章节、文件或问题类型（如引用、图） | 全面任务按 `document-quality.md` 全项；局部任务按明确范围 |
| 交付引擎 | Typst / LaTeX，或沿用现有 | 沿用项目现有引擎 |
| 是否写入 | 允许 / 只审阅 | 允许，含正文、图源、文献数据 |

读者与用途一句就足以定类型；用户已指定或项目已明确记录的沿用，不要求重复说明，也不新增元数据
字段或另一套报告模板。判断结果写进既有报告即可。

## 八、调用示例

全面检查修复两篇：

```text
按 docs 规范把 radar-data-gen 和 ai4ai 全面检查并修复，引用统一上标，完成后给 PDF 和未决清单。
```

润色，并说明读者与文种：

```text
按 docs 规范润色 <项目>，这是给工程师看的选型调研。
```

只审阅一章：

```text
按 docs 规范检查 ai4ai 第 3 章的引用与图表，只审阅，不要改文件。
```
